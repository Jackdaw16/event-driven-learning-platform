# ADR-0003: Transactional outbox and at-least-once messaging

## Context

The platform uses RabbitMQ for asynchronous payment and certificate workflows.

Several business operations must both update PostgreSQL and publish an event. For example, enrollment creation persists business state and needs to emit `EnrollmentCreated`. Completion persists the final enrollment state and needs to emit `EnrollmentCompleted`.

Publishing directly to RabbitMQ inside a database transaction creates a dual-write problem:

- the database may commit while publication fails;
- the broker may accept the event while the database transaction later rolls back;
- a crash can occur between the two operations.

PostgreSQL and RabbitMQ do not share one local transaction, and attempting to provide global exactly-once semantics would add substantial coordination complexity.

RabbitMQ delivery itself is also naturally compatible with redelivery. Consumers therefore need to tolerate duplicate messages.

## Decision

Use a **transactional outbox** for publication and design messaging around **at-least-once delivery with idempotent consumers**.

### Transactional outbox

When a business transaction needs to emit an integration event, the event is inserted into the `outbox_events` table in the same PostgreSQL transaction as the business state change.

This guarantees:

- if the business transaction rolls back, its event is not committed;
- if the business transaction commits, the event remains durably available for later publication.

An outbox worker polls unpublished events in batches.

Concurrent workers coordinate through PostgreSQL row locking with `SKIP LOCKED`, allowing work to be distributed without multiple workers intentionally processing the same pending row at the same time.

### Broker publication

RabbitMQ topology is declared explicitly in application configuration, including:

- durable exchanges;
- queues;
- bindings;
- dead-letter exchanges and queues.

Publication uses:

- publisher confirms;
- mandatory routing / returned-message detection;
- bounded confirmation waiting.

An outbox row is marked `PUBLISHED` only after positive broker confirmation.

### At-least-once semantics

There is still a crash window after RabbitMQ confirms publication but before the database records the outbox event as published.

The same event can therefore be published again.

This is accepted as an intentional property of the design rather than hidden behind an exactly-once claim.

### Idempotent consumers

Consumers use stable event IDs and a durable `processed_events` table.

Business effects and processed-event recording execute in the same local database transaction. Redelivery of an already processed event therefore becomes a no-op instead of duplicating the business effect.

Business-level constraints provide an additional layer where appropriate. Certificate issuance, for example, also enforces one certificate per enrollment, so different event IDs describing the same business completion cannot create duplicate certificates.

### Retry and dead-letter handling

Transient consumer failures use bounded retry with backoff.

Messages that still cannot be processed are rejected and routed to a dead-letter queue instead of being retried indefinitely.

Invalid message metadata or incompatible business relationships are treated as poison messages and follow the same controlled failure path.

### Event contracts

Integration events are JSON contracts separate from JPA entities.

They include transport metadata such as:

- event ID;
- event type;
- contract version;
- timestamp.

This keeps persistence models from becoming accidental message contracts and allows event formats to evolve explicitly.

## Alternatives considered

### Publish directly after the database commit

The application could commit business state and then call RabbitMQ.

This was rejected because a process or broker failure after the database commit could permanently lose the event.

### Publish to RabbitMQ before committing the database

This reverses the inconsistency: consumers could observe an event for business state that later rolls back.

### Distributed/XA transaction

PostgreSQL and RabbitMQ could theoretically be coordinated through a stronger distributed transaction mechanism.

This was rejected because it would add operational complexity and coupling disproportionate to the requirements.

### Exactly-once delivery

Exactly-once transport semantics would require stronger coordination across broker, database, and consumers.

This was rejected in favor of the simpler and explicit model:

**at-least-once delivery + idempotent processing**.

### In-memory deduplication

Processed event IDs could be held in application memory.

This was rejected because deduplication must survive restarts and work consistently across multiple application instances.

## Consequences

### Positive

- Business state and intent to publish are committed atomically.
- Temporary RabbitMQ failures do not lose committed events.
- Consumer redelivery does not duplicate business effects.
- Poison messages have a bounded retry path and visible DLQ destination.
- Multiple outbox workers can process batches concurrently.
- Message contracts are versionable and independent from persistence entities.
- The guarantees are testable using real PostgreSQL and RabbitMQ Testcontainers.

### Negative

- Event publication is eventually consistent rather than immediate.
- Duplicate publication is possible and must remain safe forever.
- Outbox and processed-event tables require lifecycle/retention consideration in a long-running production system.
- Consumers must preserve idempotency when new side effects are added.
- Operators need visibility into failed outbox publication and dead-letter queues.

## Failure semantics

The design intentionally provides **at-least-once delivery**, not global exactly-once processing.

A representative failure scenario is:

1. an outbox event is committed;
2. RabbitMQ accepts and confirms it;
3. the application crashes before marking the row `PUBLISHED`;
4. the event is published again after restart;
5. the consumer recognizes the same event ID and does not repeat the business effect.

This behavior is expected and is part of the reliability model.

## Result

The system favors durable event delivery and explicit idempotency over distributed transactions or unsupported exactly-once guarantees.
