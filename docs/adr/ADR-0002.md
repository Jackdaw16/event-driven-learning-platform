# ADR-0002: Database-enforced concurrency and transactional integrity

## Context

Enrollment creation modifies shared mutable state: the number of occupied seats in a course.

A naïve application-level sequence such as:

1. read the course;
2. check `occupiedSeats < maximumSeats`;
3. increment the value;
4. save the course;

is vulnerable to race conditions. Two concurrent requests can both observe the final free seat and both decide that enrollment is allowed.

The same workflow also needs to keep several changes consistent:

- reserve a seat;
- create an enrollment;
- create its pending payment;
- record the outbound integration event.

If any of those operations fails, the others must not remain partially committed.

Cancellation introduces a related problem: concurrent cancellation attempts must not release the same seat more than once.

## Decision

Enforce critical concurrency invariants in PostgreSQL and coordinate related state changes inside explicit Spring transactions.

### Atomic seat reservation

Seat reservation is performed through a conditional database update equivalent to:

```sql
UPDATE courses
SET occupied_seats = occupied_seats + 1
WHERE id = ?
  AND status = 'PUBLISHED'
  AND occupied_seats < maximum_seats;
```

A request owns a seat only when the database reports that one row was updated.

The capacity decision and mutation therefore happen atomically inside PostgreSQL instead of relying on a read/check/write sequence in application memory.

Seat inventory is updated through a dedicated persistence path rather than through ordinary detached entity updates, reducing the risk that unrelated course writes overwrite concurrent capacity changes.

### Transactional enrollment creation

The following operations participate in one database transaction:

- seat reservation;
- enrollment creation in `PENDING_PAYMENT`;
- pending payment creation using the course price snapshot;
- transactional outbox event recording.

A failure rolls back the complete operation, including the seat reservation.

### Cancellation

Cancellation locks the enrollment before performing the state transition.

Only cancellable states release a seat. Repeated or concurrent cancellation attempts therefore cannot decrement capacity more than once.

Seat release is performed atomically and is part of the same transaction as the enrollment state change.

### Database constraints

Application checks are complemented by database-level constraints for invariants that must survive concurrent requests and process failures, including:

- prevention of duplicate live enrollments for the same student/course;
- unique payment idempotency keys;
- unique certificate per enrollment;
- other schema-level uniqueness and referential integrity constraints.

Idempotency keys are persisted rather than held in memory so retries remain safe across application restarts.

## Alternatives considered

### Application-level synchronization

Java locks or synchronized sections could serialize requests inside one application process.

This was rejected because the invariant belongs to shared persisted data. In-memory locking would not protect the system if multiple application instances were running.

### Optimistic locking on the whole course entity

A version column with retries could detect concurrent updates.

This is a valid strategy, but the capacity requirement is simple enough to express as a single conditional SQL statement. The atomic update avoids a read-modify-write cycle and avoids retrying the whole course aggregate merely to reserve one seat.

### Pessimistic locking for every seat reservation

The course row could be selected `FOR UPDATE` before checking capacity.

This would also preserve correctness but would hold a row lock while the application performs the check and subsequent work. The conditional update provides a smaller and more explicit critical section for the capacity invariant.

Pessimistic locking is still used where serializing access to a specific enrollment transition is the clearer choice, such as cancellation and selected asynchronous workflow transitions.

## Consequences

### Positive

- Course capacity cannot exceed `maximumSeats` under concurrent requests.
- The final available seat has one database-enforced winner.
- Enrollment, payment, seat reservation, and outbox recording cannot be partially committed.
- Idempotency and uniqueness survive process restarts.
- The strategy remains correct if more than one application instance accesses the database.
- The concurrency model is demonstrable with real PostgreSQL integration tests.

### Negative

- Some persistence logic uses targeted SQL/JDBC instead of pure entity mutation.
- Database-specific concurrency behavior becomes part of the solution design.
- Pessimistic locks used in selected workflows require transactions to remain short.
- Database constraints must remain aligned with domain rules as those rules evolve.

## Verification

Integration tests use PostgreSQL Testcontainers to exercise real database behavior, including:

- concurrent requests competing for the last seat;
- duplicate enrollment protection;
- idempotent retries;
- rollback behavior;
- concurrent cancellation.

## Result

Correctness of shared capacity and transactional invariants is enforced at the database boundary, where all concurrent application instances observe the same state.
