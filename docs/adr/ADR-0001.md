# ADR-0001: Modular monolith with pragmatic hexagonal boundaries

## Context

The platform contains several business areas with different responsibilities: catalog management, students, enrollments, payments, certificates, authentication, and messaging.

The domain also contains workflows that cross those boundaries. For example, enrollment creation must reserve a course seat, create an enrollment and payment, and record an integration event atomically. Payment confirmation and certificate issuance are asynchronous.

The implementation therefore needs clear ownership boundaries, but the current scope does not require independent deployments, independent databases, or the operational complexity of a distributed microservice architecture.

A conventional layered monolith would be simpler initially, but it would make module ownership easier to erode as the application grows. At the other extreme, applying strict hexagonal architecture and DDD abstractions to every class would introduce ceremony without improving the important boundaries in this exercise.

## Decision

Implement the system as a **modular monolith with pragmatic hexagonal boundaries**.

The main application modules are:

- `catalog`: categories, instructors, and courses.
- `student`: student persistence and student-owned data.
- `enrollment`: enrollment lifecycle, capacity coordination, cancellation, progress, and relationship queries.
- `payment`: asynchronous payment processing.
- `certificate`: certificate issuance after enrollment completion.
- `auth`: authentication, JWT issuance, roles, and ownership authorization.
- `messaging`: RabbitMQ topology, transactional outbox publication, retry/DLQ configuration, and consumer reliability.
- `shared`: cross-cutting technical infrastructure without business ownership.

Each business module owns its behavior and model. Domain behavior remains independent from HTTP, Spring Security, and persistence concerns.

Application services coordinate use cases and transaction boundaries. Infrastructure adapters implement HTTP, JPA/JDBC persistence, RabbitMQ, and other framework-specific concerns.

Ports are introduced where they represent meaningful boundaries rather than mechanically wrapping every dependency.

All modules currently:

- run in one Spring Boot process;
- share one PostgreSQL database;
- participate in local database transactions where needed.

RabbitMQ is used for workflows where asynchronous communication provides a meaningful decoupling boundary, not as a substitute for direct in-process collaboration everywhere.

## Alternatives considered

### Microservices

Each business module could have been deployed independently with its own database and API/event contracts.

This was rejected for the current scope because it would introduce:

- distributed transactions or additional saga coordination;
- more network failure modes;
- service discovery and deployment concerns;
- more complex local execution and testing;
- operational overhead unrelated to the core requirements.

The current module boundaries remain useful extraction points if independent deployment becomes justified later.

### Traditional layered monolith

A single controller/service/repository structure would reduce the number of packages and abstractions.

This was rejected because the domain already contains distinct ownership boundaries and asynchronous workflows. Explicit modules make those responsibilities visible and reduce accidental coupling.

### Strict hexagonal architecture everywhere

Every dependency could be represented through ports and adapters, including trivial internal collaborators.

This was rejected because it would add ceremony without improving isolation. The architecture uses ports where they protect meaningful domain or integration boundaries.

## Consequences

### Positive

- Business ownership is explicit in the package structure.
- Local ACID transactions remain available for workflows that require them.
- The application is simple to build, test, run, and deploy as one unit.
- Framework concerns do not need to leak into the domain model.
- Asynchronous boundaries are introduced only where they provide clear value.
- Modules can be extracted later if operational or scaling requirements justify it.

### Negative

- Modules are not independently deployable.
- A shared database means physical data isolation is weaker than in database-per-service architectures.
- Package boundaries rely on design discipline rather than network isolation.
- A failure of the single application process affects all modules.

## Result

The architecture deliberately optimizes for clear boundaries and correctness without paying the operational cost of a distributed system before that cost is justified.
