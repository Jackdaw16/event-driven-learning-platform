# Context

The approved architecture is a modular monolith with pragmatic hexagonal boundaries. The initial top-level modules are `catalog`, `student`, `enrollment`, `payment`, and `certificate`.

Catalog owns Category, Instructor, and Course. Category has ACTIVE and ARCHIVED states; Course has DRAFT, PUBLISHED, and ARCHIVED states. Enrollment has PENDING_PAYMENT, ACTIVE, COMPLETED, and CANCELLED states, tracks progress from 0 to 100, and reaches COMPLETED only through the ACTIVE to COMPLETED transition at 100% progress. Payment has PENDING, CONFIRMED, and FAILED states. A confirmed payment activates its Enrollment. A certificate requires a COMPLETED enrollment. Cancellation from PENDING_PAYMENT or ACTIVE releases one seat. Refunds and reversals are not supported now.

# Decision

Create only the five top-level Java package boundaries as trackable `package-info.java` files. Preserve the modular-monolith structure and use pragmatic hexagonal boundaries as implementation is added. A future application-layer use case will coordinate the atomic enrollment transaction. Idempotency is deferred to the future application and persistence implementation.

# Consequences

This scaffold establishes module ownership without implementing entities, value objects, enums, ports, application services, persistence, messaging, security, Docker, configuration, or dependencies. It does not create infrastructure packages or alter the existing bootstrap or local infrastructure. Future work must place behavior within the owning module and respect the requirements recorded above.
